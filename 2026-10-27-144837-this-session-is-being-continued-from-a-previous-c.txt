  The trace files

  On JUPITER, I turned the two memory snapshots (.pickle) into HTML pages with
  PyTorch's own tool:

  python -m torch.cuda._memory_viz trace_plot <snapshot>.pickle -o 
  memory-<name>.html

  Then I copied the two HTML files and the Nsight file to your laptop with scp.
  Nothing in the repo changed.

  The GPU memory work

  1. Find what fills the GPU

  - Reference run dw1fgpmo, with the unchanged operan config, peaks at 31.69 GiB
    per GPU.
  - A memory snapshot of the same setup (lvzfwv01) shows what is alive at the
    peak. I analyzed it with scripts/analyze_memory_snapshot.py.
  - About 75% of the peak is activations: tensors the forward pass keeps so the
    backward pass can use them. Weights, gradients and optimizer states are
    small because FSDP splits them over the 4 GPUs.

  The biggest items:
  - Forecast engine: every layer has its own checkpoint, so it keeps 52 saved
    inputs of 96 MiB each.
  - Decoder: it copies each cell's 9 neighbor cells, which makes 2 copies of 864
    MiB.
  - Input batch: the source tokens sit on the GPU in float32.

  2. Background: checkpointing

  With checkpointing, the forward pass saves only the input of a block. The
  backward pass then recomputes the inside of the block. This trades memory for
  extra compute. The code already uses it, but often per layer, which still
  saves many inputs.

  3. Six options, each behind a config flag (all off by default)

  Option: fe_checkpoint_per_block
  Change: forecast engine: one checkpoint per attention block plus the layers
  after it, so fewer saved inputs
  Saved GiB: 1.66
  ────────────────────────────────────────
  Option: decoder_gather_after_kv_projection
  Change: decoder: compute keys and values once per cell, then pick the 9
  neighbors by index instead of copying the tokens 9 times
  Saved GiB: 1.69
  ────────────────────────────────────────
  Option: ae_local_checkpoint_per_block
  Change: local assimilation: one checkpoint per attention + MLP pair
  Saved GiB: 0.78
  ────────────────────────────────────────
  Option: pred_checkpoint_per_layer
  Change: decoder: one checkpoint per cross-attention plus the blocks after it
  Saved GiB: -2.79 (worse)
  ────────────────────────────────────────
  Option: source_tokens_in_mixed_precision
  Change: copy source tokens to the GPU as bf16, since the embedding converts
  them to bf16 anyway
  Saved GiB: 1.16
  ────────────────────────────────────────
  Option: fe_checkpoint_bf16
  Change: save forecast engine checkpoint inputs as bf16 instead of float32
  Saved GiB: 1.69

  Code locations:
  - engines.py: the checkpoint options.
  - model.py, attention.py, spatial_parallel.py: the decoder index.
  - trainer.py, batch.py, stream_data.py: the bf16 source tokens.

  One problem along the way: when one checkpoint covers several FSDP modules,
  the recompute crashed. Only part of the weights had been gathered from the
  other GPUs. I added _unshard, which gathers all of a group's weights at the
  start of the recompute. The first attempts failed (z7frx7e3, a5g9twto); the
  reruns worked.

  pred_checkpoint_per_layer makes things worse. The peak happens during the
  decoder backward, and a bigger checkpoint recomputes more at once there. It
  stays off.

  4. How each option was checked

  - Each option ran alone: 50 steps, fixed data order, compared with dw1fgpmo.
  - Loss: per step, the difference from the reference is at noise level (mean
    0.01% to 0.06%).
  - Decoder index: I also checked it directly on a GPU. The forward output is
    identical, and the gradients differ only by bf16 rounding.
  - fe_checkpoint_bf16 is the only option that changes the math, because it
    rounds the saved values.
  - Speed: no run was slower (4.3 vs 4.48 s/step). However, step time is mostly
    set by data loading, so these runs do not show the real cost of the extra
    recompute.

  5. Combined

  ┌──────────────────────────────────────┬──────────┬─────────────────┐
  │                 Run                  │ Peak GiB │      Saved      │
  ├──────────────────────────────────────┼──────────┼─────────────────┤
  │ reference dw1fgpmo                   │ 31.69    │                 │
  ├──────────────────────────────────────┼──────────┼─────────────────┤
  │ 4 exact options (zjif1x9c)           │ 28.93    │ 2.76 GiB (8.7%) │
  ├──────────────────────────────────────┼──────────┼─────────────────┤
  │ same + fe_checkpoint_bf16 (pbpl25ww) │ 28.93    │ nothing more    │
  └──────────────────────────────────────┴──────────┴─────────────────┘

  The savings do not add up (about 5.3 GiB alone, 2.76 GiB together). Once one
  phase gets smaller, another phase becomes the peak. The snapshot of the
  combined run (bnayqygv) shows where the peak is now: the stream embedding
  backward.

  The embedding runs all 9 streams in one checkpoint, so the backward recomputes
  all of them at once. That is about 10 GiB of recomputed attention plus 7 GiB
  of backward buffers.
